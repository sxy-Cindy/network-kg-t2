T1

网络设备、接口与链路资产知识图谱

网络管理与运维 难度 ★★☆ 数据可得性：高

题目 ID：t1-net-assets · 脚手架自带：12 类 / 11 关系 · 示意语料可抽 20 实体 / 38 关系

一句话：把散落在设备配置、运维台账、DCIM/IPAM 里的"设备—接口—链路—网段—角色"关系汇成资产图，回答"某设备宕机影响哪些业务网段""这条链路是否双上行"。

① 本体构建

  • 类：Device / Interface / Link / IPSubnet / IPAddress / VLAN / DeviceRole / Site / Vendor / Service / Incident
  • 关系：has_interface · connects_to(对称) · has_subnet · located_at · runs · affected_by …
  • 加分：把 YANG 模型映射为类与关系

② 三种方法

  • A 规则：配置块正则（hostname / interface / ip address / switchport）
  • B 模型：设备/接口/网段序列标注；进阶做关系分类器
  • C LLM：台账描述性文本（"这条链路上联到核心交换机"）

③ Agent 应用

  • 影响面问答：故障设备 → 受影响网段/服务（2–3 跳）
  • 配置核查：接口是否已有网关、上行是否双链路
  • Skill 或 MCP 接入 Intellect Agent

数据：NetBox ★21689（DCIM/IPAM，Apache-2.0，CSV/REST 导出，2026-10 活跃）· Batfish ★1503（配置快照与校验，Apache-2.0）· SNDlib 公开拓扑（GML，真实网络，本机可达）· 校内实验室设备配置样本（须脱敏；无实验条件者用 Batfish 自带快照样例）。⚠ Internet Topology Zoo 本机不可达。

代码入口：topics/t1-net-assets/（本体种子 · 抽取模式 · 词表 · 示意语料） · kgc/ontology.py → kgc/rule.py〡kgc/model.py〡kgc/llm.py → kgc/fuse.py → kgc/kg.py → kgc/agent_app.py；一键 bash scripts/run_all.sh t1-net-assets

参考文献：Batfish, A General Approach to Network Configuration Analysis, NSDI 2015；IETF YANG 1.1（RFC 7950，设备/接口建模上位参考）；Noy & McGuinness, Ontology Development 101（本体七步法）；ITIL 4 配置管理实践（CI 与 CI 关系）；Mininet, NSDI 2010（如需仿真拓扑）。

验收点：本体 TTL 可解析且自检 0 问题 · 三方法对金标准报 P/R/F1 · ≥3 个多跳查询题（含 1 个"图谱中无此知识"拒答题）· 答案验证器未支撑句 = 0 · 输出资产拓扑图（GraphML/Cytoscape）。

网络安全威胁情报知识图谱（CVE × CWE × CPE × ATT&CK）

网络安全 难度 ★★☆ 数据可得性：很高

题目 ID：t2-cve-attack · 脚手架自带：13 类 / 13 关系 · 示意语料可抽 11 实体 / 12 关系

一句话：跨源打通漏洞、弱点、受影响产品与攻击技术，回答"我们这批设备当前暴露什么攻击面、有没有检测覆盖"。这是跨源 ID 对齐的真实战场。

① 本体构建

  • 13 类：Vulnerability / Weakness / AttackPattern / Product / Technique / Tactic / Group / Malware / Mitigation / DetectionRule / Exploit / Advisory
  • 关系：has_weakness · affects_product · exploited_by · known_exploited · detects · mitigates …
  • ID 主键化 + 版本标注（ATT&CK 每季度更新）

② 三种方法

  • A 规则：ID 正则（CVE/CWE/CAPEC/CPE/T####）+ 结构化源直接映射
  • B 模型：安全文本 NER；对比 SecureBERT 与通用 BERT
  • C LLM：从 APT 报告/公告抽 TTP（Group uses Technique）

③ Agent 应用

  • 暴露面问答：PAN-OS 10.2 有无在野利用漏洞？对应哪条检测规则？
  • 检测覆盖分析：一组技术（T1190…）哪些有 Sigma/D3FEND 对应
  • 跨源 join 覆盖率必须抽样报告
取数范围（重要）：security-kg 全量 3136 万条 / 527.8 MB 不要全量导入。只取 cve（4,457,511 条）+ kev（19,069 条） 即可覆盖"漏洞—弱点—在野利用"主线；要加检测覆盖再取 sigma（33,498 条）。数据集按源分文件，直接选文件下载即可。

其他数据：MITRE ATT&CK STIX（mitre-attack/attack-stix-data ★699，2026-10-13 更新）· CVE 官方 API（cveawg.mitre.org，脚手架已实现）· EPSS / CISA KEV（站点 200 可达）· GraphKer（Neo4j dump，数据停 2023-09）· CVE-KGRAG（KG+RAG 应用壳 ★21）。

网络与系统日志驱动的故障根因知识图谱

AIOps / 网络运维 难度 ★★★ 数据可得性：高

题目 ID：t3-log-rca · 脚手架自带：10 类 / 10 关系 · 示意语料可抽 25 实体 / 49 关系 · 进阶层

一句话：走完"日志解析 → 事件模板 → 因果图 → 根因推理"全链条，让 Agent 能从一段日志给出候选根因链与处置动作。

① 本体构建

  • 10 类：LogTemplate / LogEvent / Host / Service / Anomaly / Fault / RootCause / Metric / Action
  • 关系：has_template · produced_by · runs_on · precedes · indicates · causes · root_cause_of · mitigated_by

  • C LLM：日志片段 → Anomaly causes Fault 与根因；对比"直接给日志"vs"先给模板"

③ Agent 应用

  • 根因问答：贴 5 条日志 → Top-3 候选根因 + 处置动作 + 证据
  • 时序因果链导出：从故障点反向遍历 causes/indicates
  • 回答必须带日志原文证据

代码入口：topics/t3-log-rca/（本体种子 · 抽取模式 · 词表 · 示意语料） · kgc/ontology.py → kgc/rule.py〡kgc/model.py〡kgc/llm.py → kgc/fuse.py → kgc/kg.py → kgc/agent_app.py；一键 bash scripts/run_all.sh t3-log-rca

验收点：日志模板抽取准确率（人工抽检 100 条或标注子集）· 因果边人工抽检精度 ≥50 条 · 时序与因果不混用 · 根因问答 Top-3 命中率 · 幻觉率不高于基线。

路由与互联网 难度 ★★★ 数据可得性：中

一句话：用归档 BGP 数据构建"AS—前缀—AS_PATH—事件"图，做路径一致性与 ROA 授权检查，用于劫持/路由泄露事件研判。

① 本体构建

  • 10 类：AS / Organization / Prefix / ASPath / Announcement / Withdrawal / ROA / HijackEvent / Collector

  • B 模型/图算法：valley-free 违背计数、MOAS 突增检测、AS_PATH 序列异常打分
  • C LLM：从事件通告抽 HijackEvent involves_as/Prefix，要求 AS 号与前缀字面出现

③ Agent 应用

  • 事件研判：AS66666 通告某 /24 是否构成劫持？授权情况如何？
  • 前缀所有权与路径检查：给定 AS_PATH 判谷底违规与 MOAS 冲突
  • 结论必须带采集点与时间窗

参考文献：Orsini et al., BGPStream, IMC 2016；Sermpezis et al., ARTEMIS: Neutralizing BGP Hijacking Within a Minute, IMC 2018；RFC 4271（BGP-4）；RFC 6480（RPKI/ROA 架构）；CAIDA AS Relationships 数据集文档（商业关系推断口径）。

验收点：≥1 采集点 × 1 小时真实 update 解析成功并给出规模统计 · ASPath 有序性在数据模型中显式体现 · 谷底违规检测召回 · ROA 覆盖率 · 报告须说明工具链停更风险。

TCP/IP 协议栈与 RFC 规范知识图谱

协议原理 难度 ★★☆ 数据可得性：很高 ★ 全组公共热身题

题目 ID：t5-protocol-rfc · 脚手架自带：11 类 / 13 关系 · 已下载 5 篇真实 RFC · 金标准 39 行

一句话：把 RFC 的文档结构（章节/引用/废弃）、协议、分层、报文域与规范关键字（RFC 2119）连成图谱，做到任何协议结论都能追到 RFC 的哪一节。此选题同时是全组第 1 周的公共热身。

① 本体构建

  • 11 类：Document→RFC / Section / Protocol / Layer / MessageField / NormativeKeyword / Obligation / Port / Extension
  • 关系：defined_in · specifies · contains · cites · obsoletes(传递) · updates · has_field · operates_at · depends_on
  • 上位参考：Dublin Core（文档元数据）、SKOS（受控词表）

② 三种方法

  • A 规则：RFC \d+、章节标题正则、RFC 2119 关键字表、ABNF（RFC 5234）、Obsoletes: 头部字段
  • B 模型：词特征 + BIO 序列标注（须做训练/评估文档分离）
  • C LLM：本体约束提示 + 证据回填 + JSON 校验（实测 F1 最高）

③ Agent 应用

  • 规范问答：IPv6 首部有哪些字段？RFC 8200 取代了谁？（带节号与原文证据）
  • 多跳溯源：TCP → depends_on → Internet Protocol → has_field → Checksum
  • 配置核查：字段取值是否符合 MUST/MUST NOT
公共热身交付（第 1 周，单独 5 分作准入）：bash scripts/run_all.sh t5-protocol-rfc 的完整日志 · data/reports/t5-protocol-rfc_eval.md 三方法指标表 · *_qa_bench.json 问答与幻觉率 · ≤3 页《三方法对比初探》· 一次成功的 MCP 工具调用。T5 也可作为正式选题，但须做实质扩展（金标准新增 ≥20 条 / 新增抽取后端或指标 / 问答集 ≥20 题并改进检索排序，三选二）。

数据：data/corpus/t5-protocol-rfc/ 随脚手架提供 5 篇真实 RFC（rfc768 / 791 / 2119 / 8200 / 9293，IETF Trust 许可可再分发）+ 金标准 39 行；可自行扩充（如 RFC 8446、RFC 9000），扩充后须过 scripts/check_gold.py 自检。

参考文献：RFC 2119 + RFC 8174（BCP 14，规范关键字语义）；RFC 9293（TCP）/ RFC 8200（IPv6）/ RFC 791 / RFC 768；RFC 5234（ABNF）；Hogan et al., arXiv:2003.02320；W3C OWL 2 Primer；Dublin Core（ISO 15836）与 SKOS（W3C Rec 2009）作上位本体。

题目 ID：t7-mlps-compliance · 脚手架自带：10 类 / 10 关系 · 示意语料可抽 17 实体 / 22 关系

一句话：把标准条款、控制项、等级、资产与合规证据连成图谱，自动做差距分析并生成整改清单。

① 本体构建

  • 10 类：Standard / Clause / ControlItem / ControlFamily（十个安全类）/ Level（一–五级）/ Asset / Evidence / Risk / Role
  • 关系：contains_clause · has_control · belongs_to_family · requires_level · applies_to · satisfied_by · catches_risk
  • "应/宜/可"的强制性差异要建模（决定整改优先级）

② 三种方法

  • A 规则：条款号正则（8.1.3.2）与标题层级解析 + 控制类词表 + 情态词映射
  • B 模型：条款文本分类（→ 控制类 / 是否技术类），中文 BERT 小样本
  • C LLM：条款 → 控制项 → 证据类型 → 风险的隐含关系抽取（规则法覆盖差，LLM 优势区）

③ Agent 应用

  • 差距分析：三级系统边界防护要求有哪些？我方证据缺哪些？
  • 整改清单：按控制类分组输出未满足项 + 责任角色 + 建议证据
  • 引用必须可回溯到标准章节号
版权红线：GB/T 22239-2019、GB/T 28448-2019 为推荐性国家标准，无再分发授权 —— 标准全文不得上传到任何仓库（含个人公开仓库）；请通过校内正版渠道/图书馆获取，仓库里只放条款编号与自写示意语料（mlps_clause_sample.txt 即为此类）。已在 tools/check_restricted_data.py 中配了机器化门禁。

数据：GB/T 22239-2019 与 GB/T 28448-2019 条款（经校内正版渠道/图书馆获取，全文不入库，仓库只放条款编号与自写示意语料 topics/t7-mlps-compliance/fixtures/mlps_clause_sample.txt）· 测评报告模板与整改单样例（课程提供）· NIST SP 800-53 Rev.5（公开，可作条款结构对照）。

代码入口：topics/t7-mlps-compliance/（本体种子 · 抽取模式 · 词表 · 示意语料） · kgc/ontology.py → kgc/rule.py〡kgc/model.py〡kgc/llm.py → kgc/fuse.py → kgc/kg.py → kgc/agent_app.py；一键 bash scripts/run_all.sh t7-mlps-compliance

参考文献：GB/T 22239-2019（基本要求）；GB/T 28448-2019（测评要求）；GB/T 25058-2019（实施指南）；GB/T 25070-2019（安全设计技术要求，可选）；《中华人民共和国网络安全法》(2016)；同 T2 的 KG 综述文献（Hogan et al., arXiv:2003.02320）。

验收点：≥3 个控制类 + 五级等级建模 · ControlItem → Evidence 关系必须由模型/LLM 产出（规则法覆盖不足要有量化证据）· 差距分析问答正确率（人工核对 10 题）· 条款编号可溯源。

坑：条款数庞大（数百条），必须先划定范围（如"第三级 安全区域边界"一节），否则进度失控。
T8

网络设备配置知识图谱与配置生成校验（进阶）

网络自动化 难度 ★★★ 数据可得性：高

题目 ID：t8-netconfig · 脚手架自带：8 类 / 7 关系（建议扩到 ≥10/≥10）· 示意语料可抽 14 实体 / 20 关系 · 进阶层

一句话：把厂商命令、配置块、意图与校验规则建成图，让 Agent 从"自然语言意图"生成配置片段并自动校验（配置即代码 / 意图网络的闭环）。

① 本体构建

  • 8 类（建议扩展）：Command / ConfigBlock / Parameter / Intent / CheckRule / Platform / Risk
  • 关系：has_param · in_block · implements · violates · causes · available_on
  • Parameter 需带取值范围；CheckRule 对齐 Batfish 检查名

② 三种方法

  • A 规则/语法：配置块缩进层级解析 + 命令正则与参数抽取；YANG 模型映射为 has_param
  • B 模型：配置块 → 业务意图分类；命令序列标注
  • C LLM：语义判断（implements / violates / causes）——规则法几乎做不到

③ Agent 应用

  • 意图→配置生成+校验："给 VLAN 20 配网关并启用 DHCP 中继"
  • 配置漂移检测：给定配置回答违反了哪些规则、引入哪些风险
  • 生成的每条命令必须能追溯到图谱中的模板

数据：Batfish 示例快照（★1503 / Apache-2.0 / 2026-10-14 活跃）· YANG 模型（YangModels/yang ★1720、openconfig/public ★995）· ciscoconfparse · 实验室配置（**须脱敏**）。

代码入口：topics/t8-netconfig/（本体种子 · 抽取模式 · 词表 · 示意语料） · kgc/ontology.py → kgc/rule.py〡kgc/model.py〡kgc/llm.py → kgc/fuse.py → kgc/kg.py → kgc/agent_app.py；一键 bash scripts/run_all.sh t8-netconfig

参考文献：Fogel et al., A General Approach to Network Configuration Analysis, NSDI 2015（Batfish 原理）；Beckett et al., A General Approach to Network Configuration Verification, SIGCOMM 2017；RFC 7950（YANG 1.1）；OpenConfig 模型文档；Mininet, NSDI 2010（可选仿真）。

验收点：≥2 个厂商配置解析成功 · 生成配置能通过校验规则（可引用 Batfish 检查）· 配置块→意图映射精度 · 生成结果可溯源到命令模板（不允许 LLM 直接编命令）。

坑：设备配置含敏感信息（同 T1）；厂商命令差异大，不要一次覆盖 3 家；校验规则必须有明确出处，否则"校验"变成主观判断。
