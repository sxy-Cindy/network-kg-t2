### 1.2 能力目标（与三阶段一一对应）

1. **本体建模能力**：能依据标准/规范/领域语料设计类、关系、属性，产出机器可读本体（OWL/RDFS），并说明设计依据与复用（上位本体、标准条款号）。
2. **知识抽取与工程能力**：能用**三种不同技术路线**（规则/模板、机器学习模型、大模型）从同一语料构建知识图谱，**用金标准量化对比**，并做融合、消歧与质量控制。
3. **知识增强应用能力**：能把图谱接入 Intellect Agent（`~/workspace/intellect-agent`）的 agent loop，做出**可溯源、可验证**的应用（问答/诊断/合规分析/配置校验），并给出幻觉率等可信度指标。
4. **工程素养**：数据来源与许可合规、实验可复现（版本、参数、脚本）、缺陷与负面结果如实报告。

### 1.3 与参考案例 `kgcase` 的关系

`kgcase` 是同一套方法学在**电力合规**域的完整落地：本体（`data/ontology/power_compliance.{json,ttl}`）→ 三方案抽取（`--scheme rule|bert|llm|ensemble`）→ 知识图谱（`data/knowledge_graph/compliance_kg*.{json,ttl,graphml,cytoscape.json}`）→ 风险分析 → RAG 问答（`scripts/compliance_qa.py`），并带金标准（`data/annotations/gold_annotations.json`）与方案对比报告（`data/reports/scheme_comparison.md`）。

本作业**沿用同一结构**，但把领域换成网络工程，并提供共享脚手架（`network/` 子项目，即 `kgcase/network`），让学生把精力集中在**领域知识与实验设计**，而不是重复写 IO 与可视化代码。

### 1.4 三阶段流水线（所有选题统一）

```
阶段一 本体构建                阶段二 知识图谱构建（三种方法）            阶段三 KG 增强应用
──────────────────           ─────────────────────────────────        ────────────────────────
标准/规范/语料                 同一语料、同一本体，三路并行               Intellect Agent loop
   ↓ 类/关系/属性               ①规则·词典·模板   （可解释、零标注）        ├ Skill 路线：技能脚本查图
本体种子 ontology.json         ②机器学习模型      （BERT/BiLSTM-CRF…）     ├ MCP 路线：图谱查询→agent 工具
   ↓ rdflib / Protégé          ③大模型抽取        （本体约束+证据回填）      ├ 检索：问题→实体→子图(带证据)
ontology.ttl (OWL) + json          ↓ 消歧/对齐/融合                        ├ 生成：只依据子图作答
   ↓ 本体自检                       ↓ 金标准评测 P/R/F1                     └ 验证：逐句核对，算幻觉率
```

**三阶段是递进依赖关系**：本体的类/关系直接约束抽取（越界实体要计数）与查询路径；阶段二的产物是阶段三唯一允许的事实来源。

### 1.5 统一技术规范（验收硬性要求）

| 项 | 规范 |
|---|---|
| 本体产物 | 每选题必须同时给出 `ontology.ttl`（OWL/RDFS，能被 rdflib/Jena 解析）与 `ontology.json`（工程视图）；类 ≥10、关系 ≥10，每项注明来源（标准条款号/上位本体/论文） |
| 本体自检 | 重复 ID、父类缺失、关系 domain/range 指向未定义类，必须为 0（脚手架 `kgc.ontology --check`） |
| 语料 | 每选题 ≥1 个**公开可追溯**数据集；报告必须写明来源 URL、版本/下载日期、许可、体积 |
| 金标准 | **20–30 条（其中关系 ≥10）**（4 周版口径，见 5.1；若时间充裕可扩到 30–60 条），**两人独立标注 + 交叉核对**，Kappa ≥0.7；金标准自检必须通过（`scripts/check_gold.py`，防止把"语料里没有的东西"写进金标准） |
| 三种方法 | 必须落在本体词汇内（越界类/关系各记为 0 或说明原因）；每条关系必须带 `evidence`（原文片段） |
| 图谱质量门槛 | ① **垃圾实体率 = 0**（纯数字/单字符标签，如 `6`、`x`）；② 受控词表类别的越词表率 = 0（如 `Layer` 只能是五个分层名之一，`fusion.controlled_classes` + `lexicons.yaml`）；③ 域值域违规边必须**列出清单并降权或说明**（本体域值域校验，类继承感知）；④ 随机抽 20 条边人工判对错，报告**人工抽检精度**（本体与自动阈值拦不住"类型合法但事实错误"的边，见 4.4 坑 8） |
| 评测 | 必须同时报告实体级与三元组级的 P/R/F1 + 越界率 + 证据覆盖率；必须说明"金标准是抽样，precision 为下界" |
| 阶段三 | 必须给出"答案 → 三元组 → 原文"三级溯源；必须给出至少 8 题的问答集与幻觉率统计；图谱未覆盖时答「图谱中无此知识」 |
| 可复现 | 一条命令跑通全流程（`scripts/run_all.sh <topic>`）+ 固定所有随机性与阈值（脚手架默认确定性：LogReg 无随机初始化、解析无采样；一旦引入随机性必须显式设种子并写进报告）+ 记录 LLM 模型与参数 |
| 图数据库与查询 | **选型不统一**：属性图库（Neo4j / Apache HugeGraph）或 RDF 三元组库（GraphDB / Apache Jena / Blazegraph）任选。两类底座的验收标准一致（≥3 条多跳查询 + 能给出源三元组），但报告必须写明选型理由、查询语言（Cypher / SPARQL / Gremlin）与查询语句原文 |
| 方法C 的 LLM 通道 | **课程不提供统一 LLM API**：方法C 一律通过 `kgc.llm --from-file <json>` 离线导入；须提交模型名与版本、使用日期、prompt 原文、原始输出文件，以及 ≥20 条人工复核记录 |

### 1.7 全组公共热身：T5 的双重角色

**背景**：本作业最大的学习风险是"三周过去了还没跑通第一版流水线"——三阶段流水线涉及本体、三路抽取、评测、Agent 接入五套概念，一旦卡在环境或流程上，后面的选题深度都无从谈起。因此把 **T5（TCP/IP 协议与 RFC 规范图谱）设为全组公共热身题**。

**"T5 为必做入门"具体指什么**（三层含义，逐条可检查）：

1. **所有组（无论最终选哪个选题）都要在第 1 周完成 T5 的完整流水线**（课内 1 学时现场演示 + 课后自跑）：用同一份真实 RFC 语料（脚手架 `fetch_corpus.py --topic t5-protocol-rfc` 已实测可下载 5 篇）跑通
   `ontology → rule → model → llm(--from-file) → fuse → kg → evaluate → agent_app`，
   并提交一份 **≤3 页的《三方法对比初探》**：必须含真实 P/R/F1 表、越界率、证据覆盖率，以及"三种方法各自擅长抽什么知识"的结论。
   参考基线（脚手架实测）：三元组 F1 = 规则 0.182 / 模型 0.044 / LLM 0.653 / 融合 召回 0.944。
2. **它是"准入检查点"，不是"选题"**：**第 1 周的准入检查点**就是 T5 热身交付物（本课程仅 4 周，热身必须在一周内消化完）。未通过者需补齐后再进入正式选题——这是把"环境/流程问题"提前暴露在计入正式评分之前，避免第 4 周答辩前才发现跑不通。
3. **它同时是"可比基线"**：所有组用同一语料、同一本体、同一评测口径，第 2 周课堂上横向对比各组的指标差异——差异只可能来自参数与实现细节，这正是讨论"评测口径与调参"最好的教学素材（例如把 `max_gap` 从 0 调到 40，规则法三元组 P 提升 50%，见 4.3(2)）。

**与正式选题的关系**：

- **T5 也可以作为正式选题**（已确认）。它同时是公共热身与候选题目；选 T5 的组须在公共基线上做**实质扩展**，满足下列任两条即可：① 金标准在本基线 39 行基础上**新增 ≥20 条**（其中关系 ≥10）；② 新增一种抽取后端或一项质量指标（如人工抽检精度、跨源 join 覆盖率）；③ 问答集扩到 ≥20 题，并给出检索排序改进的实测提升（对应 4.4 坑 2 的 Top-k 截断问题）。**参考答案已公开**，因此仅复述基线结果（同语料、同指标）不计分——评分看的是"在基线上做出了什么增量"。
- T5 热身与正式选题**分开计分**：热身建议 5 分（作为准入权重，见第 6 节），不占用正式作业 100 分。
- 教师侧收益：全组公共基线便于横向比较与答疑，也便于识别"抄基线代码但讲不清原理"的组（答辩时随机抽 T5 的某个模块要求现场解释）。

**交付物清单（第 1 周检查点）**：① `bash scripts/run_all.sh t5-protocol-rfc` 的完整运行日志；② `data/reports/t5-protocol-rfc_eval.md`（三方法指标表）；③ `data/reports/t5-protocol-rfc_qa_bench.json`（问答可回答率与幻觉率）；④ ≤3 页对比初探；⑤ 一次成功的 MCP 工具调用截图或 `scripts/mcp_smoke_client.py` 输出。

### T1 网络设备、接口与链路资产知识图谱

**背景与能力点**：把分散在设备配置、运维台账、DCIM/IPAM 系统里的"设备—接口—链路—网段—角色"关系汇成资产图，用于**影响面分析**（某设备宕机影响哪些业务网段）与**排障问答**。能力点：结构化/半结构化语料的本体化、配置文本解析、拓扑推理。

**数据集**

| 资源 | 形态 | 获取方式（实测状态） |
|---|---|---|
| NetBox（★21689 / Apache-2.0 / 2026-10-14 活跃） | DCIM/IPAM，提供 CSV/REST 导出 | `github.com/netbox-community/netbox`（可达） |
| 设备配置样本 | Cisco IOS / 华为 VRP / Juniper 文本 | 校内实验室导出；或 `mpenning/ciscoconfparse` 仓库示例（可达） |
| Batfish 示例快照 | 网络配置快照集 | `github.com/batfish/batfish`（★1503 / Apache-2.0 / 2026-10-14 活跃） |
| 公开真实拓扑 | 200+ 真实网络拓扑（GML） | SNDlib `sndlib.put.poznan.pl`（本机 200 可达）；⚠ Internet Topology Zoo（`topology-zoo.org`）本机不可达，需代理 |
| 脚手架离线示意语料 | `topics/t1-net-assets/fixtures/campus_network.txt` | 已生成，含 20 实体 / 38 关系，用于冒烟 |

**阶段一：本体**（脚手架已给 12 类 / 11 关系，学生需扩展并说明依据）
类：`Asset`(顶层) / `Device` / `Interface` / `Link` / `IPSubnet` / `IPAddress` / `VLAN` / `DeviceRole` / `Site` / `Vendor` / `Service` / `Incident`；
关系：`has_interface` `connects_to`(对称) `has_subnet` `has_role` `located_at` `made_by` `runs` `belongs_to` `serves` `affected_by` `mentioned_in`(结构关系)。
可参考的上位思路：ITIL 配置管理（CI 与 CI 关系）、IETF YANG 数据模型（`YangModels/yang` ★1720、`openconfig/public` ★995 / Apache-2.0）——**YANG 的 container/list 结构可映射为类与关系**，这是本选题的加分点。

```bash

python -m kgc.ontology --topic t1-net-assets --check # 本体自检（重复ID/父类/域值域）
```

**阶段二：三种方法**
- **方法A 规则/模板**：设备配置正则解析（`interface X` 块、`ip address`、`switchport`、`hostname`）+ 运维台账模板。脚手架 `patterns.yaml` 已给 7 条实体模式与 4 条关系模板。参考：`ciscoconfparse`、Batfish 的配置解析器。
- **方法B 模型**：把"设备/接口/网段"识别做成序列标注（词特征 + LogReg 基线 → 换成 BERT-BiLSTM-CRF）；进阶可做**关系判定分类器**（句内实体对 → 是否有 `connects_to`）。参考 `zjunlp/DeepKE`（★4484 / MIT）。
- **方法C LLM**：本体约束提示词抽取，要求"实体必须来自下文"并回填证据；适合处理描述性台账文本（"这条链路上联到核心交换机"）。

**阶段三：KG 增强应用**
- 应用一：**影响面问答**——"CORE-SW-01 故障会影响哪些网段/服务？"（2–3 跳查询，`affected_by`/`serves`/`connects_to`）。
- 应用二：**配置核查助手**——给出配置片段，Agent 查图后回答"该接口是否已有网关、上行是否双链路"。
- 集成：Skill 路线（`skills/kg-qa`）+ MCP 路线（`intellect mcp add kg ...`）。

**验收点**
1. 本体 TTL 可被 rdflib 解析，自检 0 问题；2. 三种方法各自对金标准报告实体/三元组 P/R/F1；3. 至少 3 个多跳查询题（含 1 个"图谱中无此知识"的拒答题）；4. 答案验证器未支撑句 = 0；5. 输出一张资产拓扑图（GraphML 或 Cytoscape）。

**参考文献**：Batfish, *A General Approach to Network Configuration Analysis*, NSDI 2015；IETF YANG 1.1 (RFC 7950)；Noy & McGuinness, *Ontology Development 101*；ITIL v4 配置管理章节；Mininet, NSDI 2010（如需仿真环境）。

**风险与坑**：设备配置含**敏感信息**（管理地址、密码散列、拓扑细节）——提交前必须脱敏，实验室数据不得外传；`connects_to` 是**对称关系**，实现时要避免重复边（脚手架在本体里标了 `owl:SymmetricProperty`，需在导入时去重）。

### T3 日志驱动的故障根因知识图谱

**题目 ID**：`t3-log-rca`（脚手架目录 `topics/t3-log-rca/`；下文命令中的 `<topic>` 均替换为该 ID）

**背景与能力点**：网络/系统日志是排障第一手材料，但原始日志无结构、无标签。本选题让学生走完"日志解析 → 事件模板 → 因果图 → 根因推理"全链条。能力点：日志模板抽取（log parsing）、序列/因果建模、图上的因果链推理。

**数据集**

| 资源 | 形态与规模（实测） | 获取方式 |
|---|---|---|
| **Loghub (LogPAI)** | **19 数据集 / 495,019,173 行 / ≈83.4 GiB**；其中 6 个带标注；★2880，2026-10-13 仍活跃 | `github.com/logpai/loghub`（可达）；⚠ 实际数据经 Zenodo 分发，**本机 Zenodo 不可达**，需代理或校内镜像 |
| HDFS_v1 / BGL / OpenSSH / Windows | 常用子集（HDFS_v1 1.47 GiB / 1117 万行；BGL 708.76 MiB） | 同上；建议只取 1–2 个子集（<1 GiB） |
| Loghub-2.0 评测结论 | 14 系统 / ≈36 亿行，含解析器排名 | Jiang et al., ISSTA 2024（可直接引用其排名作为基线） |
| 网络设备日志 | syslog 文本 | 实验室设备/模拟器导出（限校内） |
| 脚手架离线示意语料 | `network_device_log_sample.txt`（syslog 形态） | 已生成（25 实体 / 49 关系） |

**阶段一：本体**（10 类 / 10 关系）
类：`LogTemplate` / `LogEvent` / `Host` / `Service` / `Anomaly` / `Fault` / `RootCause` / `Metric` / `Action`。
关系：`has_template` `produced_by` `runs_on` `precedes`（时序）`indicates` `causes` `root_cause_of` `mitigated_by` `correlates_with`。
**要点**：`precedes` 是时序关系，`causes` 是因果——两者必须区分，且因果不能由共现直接推出（本选题的核心科学问题）。

**阶段二：三种方法**
- **方法A 规则/模板**：Drain/Spell 类日志解析（把日志切成 `<*>` 模板）+ 因果触发词（`caused by`/`due to`/`导致`）。参考 `logpai/logparser`、SEPSES 的 `slogert`（★20，Python 日志模板抽取）。
- **方法B 模型**：日志序列异常检测（LogBERT/DeepLog 思路的离线缩小版：模板序列 → n-gram 特征 → 分类器；或小规模 Transformer）。
- **方法C LLM**：让 LLM 从"日志片段 + 上下文"输出 `Anomaly causes Fault` 与 `RootCause`，强制给原文证据；对比零样本与"先给模板再给 LLM"的两阶段效果。
- **融合**：因果边的置信度用"多方法一致票数 + 时序约束"双重过滤。

**阶段三：KG 增强应用**
- 应用一：**根因问答**——贴一段日志（或 5 条模板），Agent 查图给出候选根因链与证据，并输出 Top-3 根因 + 处置动作。
- 应用二：**时序因果链导出**——从故障点反向遍历 `causes`/`indicates`，导出"事件—异常—根因"链。

**验收点**：1. 日志模板抽取的**解析准确率**（Parsing Accuracy，用 Loghub 标注子集或人工抽检 100 条）；2. 因果边的人工抽检精度（≥50 条，报告混淆矩阵）；3. 时序约束是否显式实现（`precedes` 与 `causes` 不混用）；4. 根因问答 Top-3 命中率；5. 幻觉率 ≤ 基线（用验证器）。

**参考文献**：Zhu et al., *Loghub: A Large Collection of System Log Datasets*, ISSRE 2023；Jiang et al., *A Large-scale Evaluation for Log Parsing Techniques*, ISSTA 2024；He et al., *Drain: An Online Log Parsing Approach*, ICWS 2017；Du et al., *DeepLog*, CCS 2017；Guo et al., *LogBERT*；SEPSES/SLOGERT（`sepses/slogert`）。

**风险与坑**：① **规模预算按 83.4 GiB / 4.95 亿行**（中文资料常写"440 GB / 17 种系统"，实测 README 为 19 个数据集 ≈83.4 GiB，差约 5 倍）；② 日志含真实内网 IP/主机名，**研究可用 ≠ 可再分发**；③ Loghub 有 v1/v2/v3 并存，实验必须钉版本。

**参考文献**：Orsini et al., *BGPStream: A Software Framework for Live and Historical BGP Data Analysis*, IMC 2016；Sermpezis et al., *ARTEMIS: Neutralizing BGP Hijacking Within a Minute*, IMC 2018；RFC 6480（RPKI/ROA 架构）；RFC 4271（BGP-4）；CAIDA AS Relationships 数据集文档。

**风险与坑**：① MRT 归档体积大，**先用 1 小时窗口**验证流水线；② 时区与时间戳口径（采集器 UTC）要统一，否则时序推理全错；③ AS 号与机构名会随时间变更，`owned_by` 必须带 `valid_time` 属性。

- **方法A 规则/模板**：`RFC \d+`、章节标题正则、RFC 2119 关键字词表、ABNF 语法抽取（RFC 5234）、引用/废弃的结构化信号（`Obsoletes:`/`Updates:` 头部字段）。
- **方法B 模型**：词特征 + BIO 序列标注基线（脚手架默认），进阶换 BERT/BiLSTM-CRF；**必须做训练/评估文档分离**，防数据泄漏。
- **方法C LLM**：本体约束提示（把类/关系定义注入 prompt）+ 证据回填 + JSON 校验 + 越界丢弃。

**阶段三：KG 增强应用**
- 应用一：**规范问答**——"IPv6 首部有哪些字段？TCP 与 Transport Layer 什么关系？RFC 8200 取代了谁？"，答案必须带 RFC 节号与原文证据。
- 应用二：**配置核查**——给定配置片段/抓包字段，Agent 查图判断"字段取值是否符合规范要求（MUST/MUST NOT）"。
- 应用三（进阶）：**多跳溯源**——`TCP → depends_on → Internet Protocol → has_field → Checksum`，导出结论链。

**验收点**：1. 本体 TTL 通过解析与自检；2. 三方法对金标准（建议扩到 60+ 条，含 20+ 关系）给出 P/R/F1；3. 金标准自检通过；4. 至少 8 题问答 + 幻觉率；5. 多跳查询至少 3 条路径正确；6. 报告须说明"precision 下界"的解读。

**参考文献**：RFC 2119 + BCP 14 / RFC 8174（关键字语义）；RFC 9293（TCP）、RFC 8200（IPv6）、RFC 791、RFC 768、RFC 5234（ABNF）；Hogan et al., *Knowledge Graphs*, arXiv:2003.02320；Noy & McGuinness, *Ontology Development 101*；W3C OWL 2 Primer。

**风险与坑**：① RFC 正文有**大量非规范内容**（前言、版权、致谢），需先切掉（脚手架按章节标题与页码行处理）；② "RFC xxxx" 的**跨文档引用会形成 191 个 RFC 节点**（实测），其中多数是噪声——需要区分"引用（cites）"与"规范定义（defined_in）"；③ 单个 RFC 内自引用（`RFC 9293` 出现在自己正文里）会造成自环，需过滤。

**本选题的特殊定位（公共热身）**：T5 同时是**全组公共热身题**（见 1.7），**第 1 周**所有组都要做一遍，因此它的语料与本体是本课程唯一的"公共参照系"。对教师的意义：① 公共基线的指标（三元组 F1 = 规则 0.182 / 模型 0.044 / LLM 0.653）可以直接用于课堂对比与评分参照；② 学生若在正式选题上卡住，可以先回到 T5 上做参数实验（如 `max_gap`、`min_prob`、检索 Top-k）验证想法，再迁移到自己的语料；③ 建议课内演示一次"把某方法精度从 X 提到 Y"的完整过程（改代码 → 跑评测 → 报指标），这是本课程最该建立的工程习惯。

- **方法C LLM**：从论文摘要/规范章节抽三元组，**强制要求 evidence 且原文片段不超过 120 字**；对比"无本体约束"与"本体约束"两种 prompt 的越界率。

**阶段三：KG 增强应用**

**参考文献**：OpenAI/OCP《Resilient AI Supercomputer Networking using MRC and SRv6》（经 OCP 发布的规范与配套论文；本机可在 `~/workspace/wiki/raw/articles/openai-mrc-supercomputer-networking.md` 查到整理稿）；RFC 8986（SRv6 Network Programming）；UEC 规范；IBTA RoCE 规范；Peng et al., *Graph RAG: A Survey*, arXiv:2408.08921。

**风险与坑**：① 前沿资料**版本更新快**（规范草案→正式发布），必须记录访问日期与版本号；② 本机 `huggingface.co` 不可达，模型需走 `hf-mirror.com` 或校内镜像；③ 容易把"厂商宣传口径"当事实——要求证据指向**规范/论文**而非营销材料。

### T7 网络安全等级保护（等保 2.0）合规知识图谱

**题目 ID**：`t7-mlps-compliance`（脚手架目录 `topics/t7-mlps-compliance/`；下文命令中的 `<topic>` 均替换为该 ID）

**背景与能力点**：等保 2.0 是安全合规的硬性要求，条款体系庞大、逐条可测评。把"标准—条款—控制项—等级—资产—证据"建成图谱，就能自动做**差距分析**与整改清单生成。能力点：规范条款的层级结构化、可测评项的建模、合规问答的可解释性。

**数据集**

| 资源 | 形态 | 获取方式（实测状态） |
|---|---|---|
| GB/T 22239-2019《网络安全等级保护基本要求》 | 标准全文 | 全国标准信息公共服务平台 `openstd.samr.gov.cn`（公开标准页）；校内图书馆/教务正版渠道 |
| GB/T 28448-2019《网络安全等级保护测评要求》 | 标准全文 | 同上 |
| 《中华人民共和国网络安全法》 | 法规全文 | 中国人大网 / 政府公开渠道 |
| 脚手架离线示意语料 | `mlps_clause_sample.txt`（编号与标题结构依据 GB/T 22239-2019） | 已生成（17 实体 / 22 关系） |

**阶段一：本体**（10 类 / 10 关系）
类：`Standard` / `Clause` / `ControlItem` / `ControlFamily`（安全物理环境/通信网络/区域边界/计算环境/管理中心 + 管理类五类）/ `Level`（一~五级）/ `Asset` / `Evidence` / `Risk` / `Role`。
关系：`contains_clause` `has_control` `belongs_to_family` `requires_level` `applies_to` `satisfied_by` `catches_risk` `owned_by_role` `quoted_from`。
**要点**：本体的"可测评性"是本选题的精髓——`ControlItem` 必须能挂 `Evidence`（证据类型：配置截图/日志/制度/测评报告），否则图谱无法支撑整改清单。

**阶段二：三种方法**
- **方法A 规则/结构**：条款编号正则（`8.1.3.2`）与标题层级解析、控制类词表匹配、`应/宜/可` 情态词映射到强制性等级。
- **方法B 模型**：条款文本分类（条款 → 控制类 / 是否技术类），可用中文 BERT（`hfl/chinese-roberta-wwm-ext`）微调或小样本分类基线。
- **方法C LLM**：条款 → 控制项 → 证据类型 → 风险的映射抽取（这是标准文本里"隐含"的关系，规则法覆盖差，LLM 优势明显）。

**阶段三：KG 增强应用**
- 应用一：**差距分析问答**——"三级系统的边界防护要求有哪些？我方已提供的证据覆盖了多少？缺哪些？"（`requires_level` + `applies_to` + `satisfied_by` 反向查缺）。
- 应用二：**整改清单生成**——按控制类分组输出"未满足项 + 责任角色 + 建议证据"。

**验收点**：1. 至少覆盖 3 个控制类、全部五级等级建模；2. `ControlItem → Evidence` 关系必须由 LLM/模型方法产出（规则法覆盖不足要有量化证据说明）；3. 差距分析问答的正确率（人工核对 10 题）；4. 条款编号可溯源到标准章节。

**参考文献**：GB/T 22239-2019；GB/T 28448-2019；《中华人民共和国网络安全法》(2016)；GB/T 25058-2019（实施指南）、GB/T 25070-2019（安全设计技术要求，可选）；同 T2 的 KG 综述文献。

**风险与坑**：① **标准文本版权**——不得把标准全文上传到公网仓库，语料只在课程环境内使用（这一点要写进作业须知）；② 条款数庞大（数百条），必须先划定范围（如"第三级 安全区域边界"一节），否则进度失控；③ "应/宜/可"的强制性差异必须建模，否则整改清单没有优先级。

### T8 网络配置知识图谱与配置生成校验（进阶选题）

**题目 ID**：`t8-netconfig`（脚手架目录 `topics/t8-netconfig/`；下文命令中的 `<topic>` 均替换为该 ID）

**背景与能力点**：从"自然语言意图"到"设备配置片段"再到"自动校验"，是网络自动化（配置即代码、意图网络）的核心闭环。本选题把命令、配置块、意图、校验规则建成图，让 Agent 用图谱生成并校验配置。能力点：厂商 CLI 语法结构建模、意图—实现映射、基于图谱的生成与校验闭环。

**数据集**

| 资源 | 形态 | 获取方式（实测状态） |
|---|---|---|
| Batfish 示例快照 | 多种厂商配置快照 + 校验规则 | `github.com/batfish/batfish`（★1503 / Apache-2.0 / 2026-10-14 活跃；含测试快照） |
| Cisco IOS / 华为 VRP / Juniper JunOS 配置 | 文本 | 实验室设备导出 / 厂商公开文档示例 |
| `ciscoconfparse` | Cisco 配置解析库 | `github.com/mpenning/ciscoconfparse`（可达） |
| YANG 模型（命令/参数结构） | YANG/OpenConfig | `YangModels/yang`（★1720）、`openconfig/public`（★995 / Apache-2.0） |
| 脚手架离线示意语料 | `device_config_sample.txt`（Cisco IOS / 华为 VRP 形态） | 已生成（14 实体 / 20 关系） |

**阶段一：本体**（8 类 / 7 关系，建议学生扩到 ≥10/≥10）
类：`Command` / `ConfigBlock` / `Parameter` / `Intent` / `CheckRule` / `Platform` / `Risk`。
关系：`has_param` `in_block` `implements` `violates` `causes` `available_on`。
**要点**：`Parameter` 需要取值范围（属性），`CheckRule` 需与 Batfish 的检查名对齐——这是"图谱能驱动校验"的前提。

**阶段二：三种方法**
- **方法A 规则/语法**：配置块解析（缩进/层级）、命令正则与参数抽取（脚手架已给 2 条配置块模式 + 1 条命令正则（覆盖 7 个命令词）+ 1 条关系模板）；YANG 模型映射为 `has_param`。
- **方法B 模型**：意图分类（配置块 → 业务意图）+ 命令序列标注；可用小样本分类器基线。
- **方法C LLM**：`ConfigBlock implements Intent`、`ConfigBlock violates CheckRule`、`ConfigBlock causes Risk` 的语义抽取（配置语义判断规则法几乎做不到，是 LLM 的优势区）。

**阶段三：KG 增强应用**
- 应用一：**意图→配置生成+校验**——"给 VLAN 20 配置网关并启用 DHCP 中继"，Agent 查图取命令模板生成配置，再用 `CheckRule` 校验。
- 应用二：**配置漂移检测**——给定配置，查图回答"违反了哪些规则/引入了哪些风险"。

**验收点**：1. 至少 2 个厂商的配置样本解析成功；2. 意图→配置的生成结果需通过校验规则（可引用 Batfish 检查）；3. 配置块 → 意图的映射精度；4. 生成结果必须能追溯到图谱中的命令模板（不允许 LLM 直接编命令）。

**参考文献**：Fogel et al., *A General Approach to Network Configuration Analysis*, NSDI 2015（Batfish）；RFC 7950（YANG 1.1）；OpenConfig 模型文档；Mininet, NSDI 2010（可选仿真）；Pan et al., arXiv:2306.08302。

**风险与坑**：① 设备配置含敏感信息（同 T1）；② 厂商命令差异大，**不要试图一次覆盖 3 家**；③ 校验规则要有明确出处（Batfish 内置检查名或自写规则 + 理由），否则"校验"变成主观判断。

### 4.3 实测结果（真实数据，可作为评分基线）

**（1）三方法对比**（5 篇真实 RFC；金标准 23 实体 / 18 三元组；`max_gap=40`、`min_prob=0.6`）

| 方法 | 实体 P | 实体 R | 实体 F1 | 三元组 P | 三元组 R | 三元组 F1 | 越界类 | 证据覆盖率 |
|---|---|---|---|---|---|---|---|---|
| A 规则/词典 | 0.077 | 0.957 | 0.142 | 0.125 | 0.333 | 0.182 | 0 | 1.00 |
| B 模型（弱监督 LogReg-BIO） | 0.069 | 0.826 | 0.128 | 0.024 | 0.278 | 0.044 | 0 | 1.00 |
| C LLM（本体约束+证据） | 0.629 | 0.957 | **0.759** | 0.516 | 0.889 | **0.653** | 0 | 1.00 |
| 融合（三路投票） | 0.055 | **1.000** | 0.105 | 0.079 | **0.944** | 0.146 | 0 | 1.00 |

**教学结论（可直接用于课堂讨论）**：
- **LLM 法在本任务上显著领先**（三元组 F1 0.653 vs 规则 0.182），因为 RFC 正文的实体—关系表达是"长距离、语义性"的，规则模板难以覆盖；但 LLM 法需要 100% 证据回填与本体校验才可用（实测拒绝率 0、越界 0，因为 prompt 强约束 + 校验丢弃）。
- **融合把召回拉到 0.944（最高）**，但精度掉到 0.071——**精确率不能靠"多方法叠加"获得**，必须靠本体约束、置信度阈值与人工校验。
- **模型法在本设置下最弱**（三元组 F1 0.044）：弱监督 + 612 训练句 + 简单词特征，出现"过度召回"（预测 3473 个实体 vs 规则 384 个）。这正好说明：**没有标注质量的提升，换模型不解决问题**——这是学生报告里最该出现的诚实结论。
- **precision 是下界**：金标准只有 23 实体，而方法抽出上百条正确但未标注的知识，全部记为误报。报告必须说明这一点，并补充人工抽检精度（建议抽 50 条算真实精度）。

**（3）融合置信度分档（实测，仅统计语义关系边，不含 `mentioned_in` 结构边）**

**（6）评审修复实测：图谱质量门槛（2026-10-14 自查发现并已修复）**

**发现**：交付的 ensemble 图谱中混入了垃圾节点与事实错误的边——

- 垃圾节点：`6`（Protocol）、`layer`（Layer）等由方法B 过度标注产生的实体；
- 无意义边：`6 / HTTP / HTTPS / OSPF / ICMP … operates_at layer` 共 12 条；
- 技术错误边：`TCP / IPv4 / IPv6 operates_at Application Layer`（应用层讨论句造成的共现误连）。

**根因**：本体的 domain/range 只约束**类型**（`operates_at` 的 Protocol→Layer 类型合法），管不住**标签内容**与**事实**；而融合层此前没有任何内容门槛，三方法的噪声被无条件并入图谱。

**修复（三层，全部记录丢弃清单，不静默删除）**：

1. `is_valid_label()` 标签质量门槛：长度 <2 或纯数字的标签一律丢弃（刻意保守——`10.10.20.0/24`、`AS12345` 这类合法领域标签不能误杀）；
2. `fusion.controlled_classes: [Layer]` 受控词表校验：`Layer` 标签必须落在 `lexicons.yaml` 的五个分层名之内（这条精确拦住 `layer`，且不影响无词表的类）；
3. `check_domain_range()` **类继承感知**的域值域校验：`cites: Document→Document` 对 `RFC→RFC` 合法（不做继承展开会误判 135 条合法边——实测踩过），违规边降权 0.5× 并在报告中列出。

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 垃圾实体（纯数字/单字符） | 12 | **0** | 清除 |
| `Layer` 节点集合 | 5 个（含 `layer`） | **4 个**（合法分层名） | 清除垃圾节点 |
| 无意义边 `X operates_at layer` | 12 条 | **0 条** | 清除 |
| 域值域违规检出 | 无机制 | **1 条**（`IPv6 operates_at Internet Protocol`，已降权） | 机制建立 |
| 融合 三元组 P | 0.0705 | **0.0791** | +12% |
| 融合 三元组 F1 | 0.1313 | **0.1459** | +11% |
| 融合 1 票边精度 | 0.0556 | **0.0640** | +15% |

**残留问题（如实标注，不掩盖）**：`TCP operates_at Application Layer` 这类"类型合法、事实错误"的边仍然存在——本体校验与阈值都拦不住。**结论**：图谱可信度必须由"本体约束 + 受控词表 + **人工抽检**"三者共同保证，这正是 §1.5 新增"随机抽 20 条边人工判对错"验收项的原因。

### 4.4 实测踩到的 8 个坑（建议直接写进实验指导书）

1. **文档节点是"超级枢纽"**：结构关系 `mentioned_in` 让 `doc:xxx` 连接全部实体，导致任意两实体 2 跳可达、最短路径失去意义（实测 `RFC 9293 → Transport Layer` 曾走成 `RFC 9293 → rfc9293 → Transport Layer`）。**修复**：路径查询排除 `Document` 类节点（`kgc/agent_tools.py` 已实现），修复后路径为 `RFC 9293 → RFC 8200 → IPv6 → Transport Layer`（3 跳语义链）。
2. **置信度截断会丢关键事实**：实测"TCP 工作在协议栈的哪一层？"检索失败（覆盖率 0.0）。逐条核对检索结果发现：`TCP operates_at Transport Layer` 置信度 0.4，而 12 个检索配额中 4 个被 `mentioned_in` 结构边占用，剩下 8 个被 `has_field`（0.6–1.0）占满，**该边在 0.4 处与 `depends_on` 并列后被排在第 13 位**——不是"没有这条知识"，而是"配额与排序把它挤掉了"。**修复方向**：① 检索时排除结构关系（`mentioned_in` 不参与事实检索）；② 先按"与问题实体直接相邻"过滤，再按置信度排序；③ 提高 Top-k 或按关系多样性分配配额。
3. **金标准容易写错**：首版 26 条金标准中有 5 条（含 1 条事实错误 `RFC 8200 cites RFC 2119`）在语料里根本不存在字面量，会无理由压低所有方法的召回。**修复**：`scripts/check_gold.py` 强制自检。
4. **规则法的"句内共现"会造假边**：实测抽出了 `IPv6 operates_at Transport Layer` 这种技术上是错的边（因为规范里讨论 TLS/SSH 时同在句中讨论 IPv6）。**修复**：触发词—目标邻近窗口约束（4.3(2) 的改进）。
5. **验证器对"正确拒答"会误判**：答案"图谱中无此知识"这一正确行为因为没有可匹配的三元组而被标为"未支撑"。**修复**：验证器需增加"拒答白名单"规则，或把该情形单列统计。
6. **本机网络通道不均**：`huggingface.co`/`google.com`/NVD 不可达或 403，但 `hf-mirror.com`/RFC 官网/ATT&CK/CVE API 可达。**修复**：`fetch_corpus.py` 对每个资源显式打印成功/失败与替代方案，绝不静默造数据。
7. **标签归一化口径会虚假抬高指标**：首版 Section 标签只取章节编号（`1`、`1.1`、`2`…），大量章节实体因标签相同而在对齐时被去重合并，预测实体数偏少 → 精度虚高。修正标签模板（`{1} {2}` 带标题）后，规则法实体 F1 从 **0.156 降到 0.1424**——**指标下降才是真相**。教训：报告必须写明实体归一化口径（按标签？按类型+标签？是否大小写/全半角归一），否则跨组数字不可比。
8. **本体管不住标签内容**：本体只约束类/关系名，因此方法B 造出的 `6`/`layer`、以及 `TCP operates_at Application Layer`（类型合法但事实错误）全部逃得过域值域校验。**修复**见 4.3(6)：标签门槛 + 受控词表 + 人工抽检，三者缺一不可。附带教训：`tools/gen_topics.py` 里改一处 `label_template` 要同步 `topics/<id>/patterns.yaml`（脚手架用 `--force` 重新生成才不会漂移）。

**答辩形式说明（已确认）**：答辩 = **演示系统 + 讲解代码 + 代码提问**，不采用"PPT 汇报"形式。建议流程：① 现场跑一条命令（如 `bash scripts/run_all.sh <topic>` 或一次 MCP 工具调用）证明系统可用（2 分钟）；② 学生自选 1 个模块讲清数据流与关键取舍（3 分钟）；③ 教师/其他组就代码提问（3–5 分钟），提问库建议从以下角度出题：

- 参数敏感性：脚手架的 `max_gap`、`min_prob`、检索 Top-k、融合权重，改一个会怎样？（可用 T5 实测数据对照）
- 评测口径：金标准为什么是抽样？为什么 precision 是下界？如果把金标准扩到 200 条，指标会怎么变？
- 失败归因：方法B 的三元组 F1 只有 0.044，是模型问题还是标注/特征问题？给出你的证据。
- 本体作用：如果删掉本体校验，越界率与 LLM 幻觉率会怎么变？
- 阶段三可信度：怎么证明你的答案不是模型记忆而是来自图谱？（三级溯源链）
- 数据合规：你的数据从哪来、许可是什么、哪些材料做了脱敏？如果要把成果公开，哪一部分必须先拿掉？（对照 `network/docs/数据分发与合规.md`）

**公共热身（T5）计分（独立于上表 100 分）**：5 分。评分点：《三方法对比初探》的指标真实性（能复现）2 分、结论深度（回答"三种方法各自擅长什么、代价是什么"）2 分、流程完整性（`run_all.sh` 日志 + 一次图谱查询成功）1 分。**该分作为准入权重**：未取得该 5 分者需在补齐后才能提交正式作业的最终版。

## 7. 其它需要考虑的内容

1. **LLM 通道（课程不提供统一 API）——方法C 的作业组织方式**：既然没有统一 API，方法C 统一走**离线导入**路径，流程固定为三步：① 学生自行选用任一可用 LLM（本地 Ollama/vLLM + Qwen 系列；或云端服务；或网页版对话框）；② **用脚手架直接生成提示词包** `python scripts/make_llm_prompt.py --topic <topic>`（产出 `data/llm_output/<topic>_prompt.md`：本体类/关系定义 + 输出 JSON 结构 + 规则 + 已切好的语料片段，可直接复制粘贴给任意 LLM；T5 实测生成 12 个片段，本体注入 11 类 / 13 关系），把返回结果按模板 `data/llm_output/_TEMPLATE.json` 整理成 `<topic>_agent_llm.json`；③ 用 `python -m kgc.llm --topic <topic> --from-file ...` 灌入流水线，后续融合与评测不需要网络。**必须随作业提交**：模型名与版本、使用日期、prompt 原文、原始输出文件、≥20 条人工复核记录（逐条判断"抽出的三元组是否被原文支持"）。这样即使各组用的是不同 LLM，评测仍可复现、可横向对比；教师也可用同一份原始输出复核。T5 实测 token 量级很小（5 篇 RFC 约 450 KB 文本），网页版逐段粘贴完全可完成；若组内有机器，建议装 Ollama + Qwen2.5-7B 作为首选（同时避免数据外传）。
2. **数据许可与受限材料分发边界（评估结论与执行机制见 [`docs/数据分发与合规.md`](数据分发与合规.md)）**：结论是"**公开方法与脚手架产物，不公开受约束材料**"——① GB/T 标准全文（推荐性标准，无再分发授权）不入任何仓库，**包括学生的个人公开仓库**，学生经校内正版渠道获取、报告中只引条款号；② 设备配置与自采日志必须脱敏，且建议仅置于私有仓库；③ 第三方数据集（security-kg/Loghub 等）只放**获取脚本 + 数据集 ID + 逐源许可表**，不复制数据本体（T2 建议只取 `cve`+`kev` 切片）；④ RFC 全文可再分发（已入库 5 篇）。仓库已配**机器化门禁** `tools/check_restricted_data.py`（全仓扫描实测 154 个文本文件 / 0 问题；白名单按 sha256 内容指纹判定，自造示意语料自动放行），并可用 `--staged` 接 pre-commit；`.gitignore` 已按类别忽略 `restricted/`、`device-configs/`、`lab-logs/`、`*.pcap*`、`*.parquet`、`*.pem`、`*.key`。
3. **防抄袭与差异化（参考答案已公开，故此条权重更高）**：① 同一选题的不同组必须用**不同语料子集或不同子域**（例如 T2 一组做"漏洞—产品"、一组做"技术—检测覆盖"）；② 学生在**个人 GitHub/Gitee 空间**提交，教师按个人仓库的提交历史与 diff 核对"增量"；③ 答辩以**讲代码 + 针对代码提问**为主（见 §6），"复制基线但不理解"会在提问环节暴露；④ 答辩时随机抽取其金标准条目，要求现场解释来源与判定依据。
4. **AI 辅助的边界**：允许用 LLM/Agent 辅助写代码与分析，但**必须提交自己的实验记录**（命令、参数、原始输出），且答辩时会追问"为什么这么设计"。脚手架本身可以作为被检视对象——学生要能讲清每个模块的作用。
5. **常见失败模式（提前预警）**：① 本体过度设计（设计 30 个类，语料支撑不了 5 个）；② 规则法写得太宽导致精度崩溃而不自知（必须看 precision 下界与人工抽检）；③ 只报 P/R/F1 不报"金标准规模"导致结论不可信；④ 阶段三直接让 LLM 自由回答，没有验证环节（这是最容易被扣分的项）。
6. **设备的"不可达资源"预案**：`huggingface.co`/NVD/Topology Zoo 本机不可达；应提前在校内镜像或 Docker 中准备（`hf-mirror.com` 镜像、ATT&CK STIX 直链、SNDlib 拓扑）。
7. **教学衔接**：`~/workspace/kgcase/power`（电力合规案例）与 `~/workspace/Protege_操作手册.md`（已有）可直接作为阶段一的入门材料；`power/docs/phase1|2|3/*.md` 提供了三阶段技术报告的写作范例（与 `network/` 脚手架同结构，可作报告模板）。
